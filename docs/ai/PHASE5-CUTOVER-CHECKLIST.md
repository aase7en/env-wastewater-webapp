## 1. ภาพรวม — dual-run คืออะไร ทำไมต้อง ≥14 วัน

Dual-run = พนักงานบันทึกข้อมูล **สองระบบพร้อมกัน** (AppSheet เดิม + ENV ใหม่)
ทุกวัน **ไม่น้อยกว่า 14 วัน** เพื่อพิสูจน์ว่า ENV จับข้อมูลได้ครบและตรงกันก่อน
"ตัดสลับ" ไปใช้ ENV อย่างเดียว ระหว่างนี้เจ้าของ/ผู้ดูแลรันเครื่องมือตรวจ parity
รายวัน:

```bash
# อ่านอย่างเดียว 100% — ไม่เขียนฐานข้อมูล ไม่เขียน Drive
python3 scripts/phase5_parity_check.py --out reports/phase5-parity-<วันที่>.md
```

รายงานที่ได้ (ภาษาไทย) เทียบต่อโดเมน: จำนวนแถว, ช่วงวันที่, นับรายเดือน,
รายการวันที่ขาด (ความซื่อสัตย์ปฏิทิน — ระบุไว้ ไม่เติมค่า), และ % ครอบคลุม
(ระบุตัวหารทุกครั้ง) โดเมนที่แหล่ง AppSheet ยังไม่ถูกแชร์จะแสดงหัวข้อ
**ยังไม่มีแหล่งข้อมูล** อย่างตรงไปตรงมา (ไม่มีวันอ้างว่า parity ผ่านโดยไม่มีแหล่ง)

## 2. โปรโตคอล dual-run ≥14 วัน (P5.1 — เตรียมพร้อม, เริ่มเมื่อเจ้าของสั่ง)

### 2.1 กิจวัตรประจำวันของพนักงาน (ทุกวันทำการ ตลอด 14 วัน)

ทำ **ตามลำดับเดิมของงานจริง** — บันทึกใน ENV หลังบันทึกใน AppSheet ทันทีที่ทำเสร็จในแต่ละจุด (ไม่สะสมท้ายวัน):

| ลำดับ | งาน | บันทึกใน AppSheet (ตาราง) | บันทึกใน ENV (หน้า/ตาราง) | เวลาที่ควรทำ |
|---|---|---|---|---|
| 1 | บันทึกคุณภาพน้ำบ่อบำบัดรายวัน | ข้อมูลคุณภาพน้ำ | หน้าฟอร์มรายวัน (`/form` → `wastewater.reading`) | ต้นกะ / หลังเดินเก็บค่า |
| 2 | บันทึกงานสวน | งานสวน tab `job` | หน้างานสวน (`core.job_log`) | หลังทำงานเสร็จจุดนั้น |
| 3 | ตรวจถังดับเพลิง (ตามรอบ) | tab `ตรวจสอบถัง` | หน้าตรวจถังดับเพลิง (`safety.extinguisher_inspection`) | ตามรอบที่กำหนด |
| 4 | ตรวจไฟฉุกเฉิน (ตามรอบ) | tab `Check` | หน้าตรวจไฟฉุกเฉิน (`safety.emergency_light_check`) | ตามรอบที่กำหนด |
| 5 | เทียบมาตรฐานเครื่องมือ (ตามรอบ) | tab `maintaining` | หน้าเทียบมาตรฐาน (`core.item_calibration`) | ตามรอบที่กำหนด |
| 6 | ตรวจ coliform (เมื่อมีการเก็บตัวอย่าง) | (แหล่งยังไม่แชร์ — ดู §5) | หน้า `/food` (`food.lab_test`) | ตามรอบที่กำหนด |

**กติกาเหล็กของ dual-run:**

1. **ห้ามข้ามฝั่งใดฝั่งหนึ่ง** — บันทึกไม่ครบสองระบบในวันนั้น = ขึ้น friction log (§3)
2. **บันทึก ENV ต้องใช้ข้อมูลเดียวกับที่บันทึก AppSheet** — ห้ามเดา/เติมค่าที่จำไม่ได้
3. **ค่าที่ไม่รู้ = ปล่อยว่าง/NULL** ห้ามใส่ 0 แทนค่าที่ไม่ทราบ (unknown ≠ zero)
4. พบหน้า ENV ใช้งานไม่ได้/แตกต่างจนบันทึกไม่ลงตัว → หยุด ขึ้น friction log ทันที แล้วบันทึก AppSheet ต่อให้งานเดิน (AppSheet ยังเป็นระบบหลักตลอด dual-run)

### 2.2 กิจวัตรประจำวันของผู้ดูแลระบบ (วันทำการ)

1. รัน `python3 scripts/phase5_parity_check.py --out reports/phase5-parity-<YYYY-MM-DD>.md`
2. เทียบสรุปท้ายรายงานกับวันก่อน: โดเมนที่ "ต่างกัน" ต้องมีสาเหตุใน friction log ภายในวันเดียวกัน
3. เก็บไฟล์รายงานไว้ครบทุกวัน — ชุดไฟล์ 14 วันนี้คือ **หลักฐานวันยอมรับ (Day-14 evidence)**

### 2.3 สัญญาณเริ่ม/หยุด

- 🚧**เจ้าของตัดสิน** — ประกาศวันเริ่ม dual-run เป็นลายลักษณ์อักษร (วัน เดือน ปี พ.ศ. + ผู้รับผิดชอบ) ก่อนพนักงานเริ่มบันทึกสองระบบ ห้ามเริ่มโดยไม่มีประกาศนี้
- 🚧**เจ้าของตัดสิน** — ต่อวันเมื่อครบ 14 วัน: ถ้ายังไม่ผ่านเกณฑ์ §4 ให้ต่อออกไปและบันทึกเหตุผล (dual-run ต่อได้ ไม่มีค่าใช้จ่ายแฝง)
- 🚧**เจ้าของตัดสิน** — การเปิดใช้ Telegram notify / cron ตรวจ parity อัตโนมัติ (ถ้าต้องการ) เป็นของเจ้าของ — โทเค็นต้องผ่าน `supabase secrets` เท่านั้น ห้าม commit ทุกกรณี (ตามคำตอบ B5)

## 3. แบบฟอร์ม Friction Log (บันทึกความขัดข้อง/ความต่างระหว่างสองระบบ)

**หลักการ:** ฟอร์มเบา ๆ ใช้ได้ทันที — **ไม่สร้างตารางใหม่ในฐานข้อมูล**
พนักงานคัดลอกแม่แบบด้านล่างไปกรอกในไฟล์เดียวต่อทีม (เช่น Google Doc / สมุดบันทึกหน้าว่างท้ายเล่ม) — วันละกี่รายการก็ได้ พิมพ์สั้น ๆ พอ

### แม่แบบบันทึก (คัดลอกไปใช้ได้เลย)

```
วันที่ (พ.ศ.): 21/11/2569
ผู้พบ:
โดเมน: บ่อบำบัด / งานสวน / ถังดับเพลิง / ไฟฉุกเฉิน / เทียบมาตรฐาน / coliform / อื่น ๆ
ฝั่งที่มีปัญหา: ENV / AppSheet / ทั้งคู่
อะไรต่างกัน: (เช่น "จำนวนแถววันนี้ ENV 2 แถว AppSheet 3 แถว", "ปุ่มบันทึกหน้าฟอร์มกดแล้วค้าง", "วันที่ขาดในรายงาน parity")
ทำอะไรแก้เรื่อง: (เช่น "บันทึก AppSheet ต่อไปก่อน แจ้งผู้ดูแลระบบแล้ว")
สถานะ: เปิด / แก้แล้ว (วันที่แก้ พ.ศ.)
```

### การจำแนก — Blocker หรือ Friction

| ระดับ | นิยาม | การจัดการ |
|---|---|---|
| **Blocker** (ห้ามเงียบ) | ENV บันทึกไม่ลงเลย · ข้อมูลหาย/ผิดฝั่ง ENV · parity ต่างกันแบบไม่มีคำอธิบายนับต่อเนื่อง ≥2 วันในโดเมนเดียว | แจ้งผู้ดูแลระบบ **วันเดียวกัน**; พิจารณาหยุดนับวัน dual-run ของโดเมนนั้น (นับใหม่หลังแก้) |
| **Friction** (นับไว้ แก้ระหว่างทาง) | ใช้ได้แต่ลำบาก (กดหลายจุด/โหลดช้า/คำศัพท์เข้าใจยาก) · ต่างกันแล้วมีสาเหตุชัด (เช่น บันทึกสายข้ามเที่ยง) | บันทึกไว้ใน log; สรุปรวมท้าย dual-run เสนอเจ้าของ |

**จำไว้:** ความขัดข้องที่โผล่ใน friction log ไม่ใช่ความล้มเหลว — การไม่บันทึกต่างหากที่ทำให้วัน Day-14 ยืนไม่ได้

## 4. เกณฑ์ยอมรับต่อโดเมน (operationalize จาก DoD ของแผน)

**DoD ของเฟส (แผน §6 บรรทัด 276 — คงข้อความเดิม):**

> (1) จำนวนบันทึก/วันของ ENV = AppSheet ทุกวันในช่วง dual-run, (2) สุ่มตรวจรายวัน ≥98% ตรง, (3) ประวัติที่ย้ายตรวจนับผ่าน, (4) เจ้าของยืนยันเป็นลายลักษณ์อักษรว่าเลิกบันทึกใน AppSheet, (5) AppSheet คงสิทธิ์อ่าน ≥90 วันเป็น rollback

**แปลงเป็นทางปฏิบัติต่อโดเมน** (ใช้รายงาน parity ประจำวันเป็นหลักฐาน):

| โดเมน | ตาราง ENV | เงื่อนไข "ผ่าน" วัน Day-14 |
|---|---|---|
| บ่อบำบัด รายวัน | `wastewater.reading` | จำนวนแถวทุกวันของ dual-run เท่ากัน · วันที่ขาด = ไม่มีหรือมีคำอธิบายใน friction log · สุ่มตรวจรายวัน ≥98% ค่าตรงทุกช่องที่ ENV ครอบ |
| งานสวน | `core.job_log` (+`core.location_area`) | เช่นเดียวกัน — จำนวน/วันที่ตรง สุ่ม ≥98% |
| ถังดับเพลิง (ตรวจ) | `safety.extinguisher_inspection` | ตามรอบตรวจ — แถวตรงครบ (master ยังไม่มีแหล่ง ดู §5 — ไม่ถ่วงการยอมรับของโดเมนตรวจ) |
| ไฟฉุกเฉิน | `safety.emergency_light_check` (+`safety.emergency_light`) | แถวตรวจตรงครบ; master 48 แถวตรวจนับซ้ำผ่าน (เงื่อนไข DoD ข้อ 3) |
| เทียบมาตรฐาน | `core.item_calibration` | แถวตรงครบ |
| coliform | `food.lab_test` | หากแหล่ง AppSheet ยังไม่แชร์: ENV เป็นฝั่งบันทึกเดี่ยวชั่วคราว — ยอมรับแบบมีเงื่อนไข (เจ้าของรับทราบเป็นลายเขียน) หรือเลื่อนยอมรับจนกว่าจะมีแหล่งเทียบ 🚧เจ้าของตัดสิน |
| คู่มือ / master / ที่อยู่ | `core.manual_*`, `core.address`, `core.distributor` ฯลฯ | เป็นตารางอ้างอิง — ตรวจนับครั้งเดียวตอนเริ่ม dual-run พอ (ตรวจนับผ่าน = เงื่อนไขข้อ 3) |
| โดเมนที่รายงานขึ้น **ยังไม่มีแหล่งข้อมูล** | — | **ไม่นับเป็นผ่าน/ไม่ผ่าน** — สถานะคือ "ยังตรวจไม่ได้" ต้องแก้ที่ต้นทาง (เจ้าของแชร์ชีต) ก่อน 🚧เจ้าของตัดสิน |

เงื่อนไขข้อ 4 และ 5 เป็นของทั้งระบบ ไม่แยกโดเมน — ยอมรับได้เมื่อ **เจ้าของเซ็นยืนยัน** (§6) และ AppSheet ถูกตั้งค่าอ่านอย่างเดียวคงไว้ ≥90 วัน

## 5. ทะเบียนงาน backfill — ชีตที่ยังไม่ถูกแชร์ (P5.2 เตรียมเป็นทะเบียนเท่านั้น)

**การรัน backfill เป็นของเจ้าของ** 🚧**เจ้าของตัดสิน** — เมื่อเจ้าของแชร์ชีตใด ผู้ดูแลจะทำ guarded seed ตามแบบแผนที่ผ่านการรีวิวของโปรแกรม parity (WHERE NOT EXISTS, blanks⇒NULL, ตัวเลขไม่เดา) แล้วรันตรวจซ้ำหลังย้ายตาม DoD ข้อ 3

| # | แหล่ง AppSheet ที่ยังไม่แชร์ | ตาราง ENV ปลายทาง | สถานะปัจจุบัน (ณ 21 พ.ย. 2569) | เมื่อเจ้าของแชร์แล้ว (auto-seed) |
|---|---|---|---|---|
| 1 | ข้อมูลถังดับเพลิง (master) | `safety.fire_extinguisher` | 0 แถว (SOURCE_UNAVAILABLE ตั้งแต่ P2.1) | guarded seed ตามแบบ P2.1 + ตรวจนับซ้ำ |
| 2 | คู่มือน้ำประปา (workbook น้ำประปา) | `core.manual_water_supply` | 0 แถว (SOURCE_UNAVAILABLE ตั้งแต่ P3.5) | guarded seed ตามแบบ คู่มือบ่อบำบัด (10/10, link-only) |
| 3 | coliform bac._Water | `food.lab_test` (จุดเก็บน้ำ) | 0 แถว (SOURCE_UNAVAILABLE ตั้งแต่ P2.4) | seed ประวัติ + ตรวจซ้ำ |
| 4 | coliform bac. Food. | `food.lab_test` (อาหาร) | 0 แถว | เช่นเดียวกัน |
| 5 | coliform bac. Employee | `food.lab_test` (พนักงาน) | 0 แถว | เช่นเดียวกัน |
| 6 | Items / Vendors / Categories (workbook) | `core.item`, `core.vendor`, `core.item_category` | 0 แถวทั้งสาม (SOURCE_UNAVAILABLE ตั้งแต่ P3.1) | guarded seed + FK เชื่อม `food.lab_test` อุปกรณ์จะเริ่ม resolve |
| 7 | Inventory (คลังเคมี) | `chemical.inventory_lot` | 0 แถว (P3.2) | guarded seed lot/MFG/EXP |
| 8 | workbook ปฏิบัติการน้ำประปา | `water_supply.daily_check` | อ่านรายวันบางส่วนผ่าน ENV อยู่แล้ว — ประวัติรอแหล่ง | seed ประวัติตามที่ชีตมี |

หมายเหตุความซื่อสัตย์: จำนวน "≈6 กลุ่มแหล่ง" ในเอกสารยุควางแผนรวมกลุ่ม 3–5 (coliform ×3) เป็นกลุ่มเดียว — ทะเบียนข้างบนฉบับนี้แจกแจงเป็นรายชีตจริง (8 บรรทัด) ตรวจซ้ำได้จากรายงาน parity ทุกครั้งที่รัน (หัวข้อ **ยังไม่มีแหล่งข้อมูล** = รายการที่ยังรอแชร์ ณ วันรัน นับสดเสมอ)

## 6. เช็กลิสต์ rollback / เลิกใช้ AppSheet (P5.3 เตรียมเป็นเช็กลิสต์เท่านั้น)

ลำดับที่แผนกำหนด: **freeze → read-only ≥90 วัน → archive export → เลิกใช้**

### ขั้นที่ 1 — Freeze (ห้ามเขียน AppSheet)

- [ ] 🚧**เจ้าของตัดสิน** — วัน freeze (ต้องเป็นวันที่ dual-run ผ่านเกณฑ์ §4 ครบ และเจ้าของเซ็นยืนยันข้อ 4 แล้วเท่านั้น)
- [ ] 🚧**เจ้าของตัดสิน** — ประกาศต่อทีม: "ตั้งแต่วันที่ ___ (พ.ศ.) บันทึกใน ENV อย่างเดียว AppSheet ห้ามเขียน"
- [ ] เจ้าของ/ผู้ดูแลตั้งสิทธิ์ AppSheet เป็น **read-only** (ปิดการเขียนทุกตาราง) — ทำใน AppSheet/Drive โดยเจ้าของบัญชีเท่านั้น
- [ ] รัน parity checker อีกครั้งวัน freeze — เก็บรายงานเป็นหลักฐานปิดฝั่ง AppSheet

### ขั้นที่ 2 — Read-only ≥90 วัน (rollback window)

- [ ] จับวันเริ่มนับ 90 วัน = วัน freeze (บันทึก พ.ศ.)
- [ ] เจ้าของยังมีสิทธิ์อ่าน AppSheet ครบทุกตารางตลอด 90 วัน (เงื่อนไข DoD ข้อ 5)
- [ ] ห้ามลบ workbook/tab/ไฟล์ใดในช่วงนี้เด็ดขาด

**เกณฑ์ rollback (กลับไปใช้ AppSheet เป็นระบบหลัก)** — ทำได้ตลอด 90 วัน ถ้า:

- [ ] ENV ทำข้อมูลหาย/บันทึกพลาดร้ายแรงที่แก้ไม่ได้ภายในวันเดียวกัน
- [ ] parity หลังตัดสลับสวนทาง (ENV น้อยกว่าที่ควรจริง ๆ) โดยไม่มีคำอธิบาย ≥2 วัน
- [ ] 🚧**เจ้าของตัดสิน** — เจ้าของพิจารณาแล้วว่าควร rollback (ตัดสินใจได้เอง ไม่ต้องรอบั๊ก)

ขั้น rollback: เปิดสิทธิ์เขียน AppSheet คืน → แจ้งทีมบันทึกสองระบบอีกครั้ง → บันทึกสาเหตุ + บทเรียนก่อนพยายามใหม่

**ข้อความปิดท้าย (ความซื่อสัตย์):** รายงาน parity และเช็กลิสต์นี้เป็น **หลักฐานประกอบ** การตัดสินใจของเจ้าของ — **ไม่ใช่**การแทนคำยืนยันของเจ้าของ (DoD ข้อ 4 ยังต้องเป็นลายลักษณ์อักษรจากเจ้าของเสมอ) ค่าทุกค่าที่เครื่องมือแสดงคือค่า ณ เวลาอ่าน (point-in-time) ไม่ใช่ live telemetry และโดเมนที่ยังไม่มีแหล่งข้อมูลจะไม่มีวันถูกนับเป็น 0-vs-0 parity
